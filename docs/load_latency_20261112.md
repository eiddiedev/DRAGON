## 历史证据与限制

没有每一版本的连续CPU记录，不能准确断言从某一版开始卡。可追溯拐点是音乐内嵌及古书/UI图片内嵌后脚本大幅膨胀，并反复导入留下重复文件。HANDOFF.md已记录17MB脚本阶段出现保存崩溃，压小后保存成功。Git快照尺寸见assets/load_audit_20261112/version-sizes.json。
前次隔离副本移除183MB历史脚本，加载后CPU约3.2%–3.4%；放回后升至约179.5%。这是扫描负担的证据，仍受加载阶段差异影响，不是严格充分根因证明。
当前证据主要指向本地加载、文件处理和大字符串分配。没有服务器监控，不能排除网络等待，但服务器拥堵无法充分解释本地文件处理CPU热点。不能认定战斗粒子是主要原因；需独立副本禁用特效的单变量加载对照才能确认。

## 建议顺序

1. 退出预览、保存并关闭当前工程后，复核依赖，将未引用历史脚本目录移至工程外持久备份；不删除最新模型/玩法。不要在加载中热移文件触发更多扫描。
2. 用相同场景与相同启动方式测加载耗时、主进程CPU、进场后帧时间。
3. 将音乐改为正规AudioClip资源，UI图片改资源引用，减小Lua内嵌字符串，保持界面和玩法功能。
4. 若仍慢，独立副本单变量禁用战斗特效初始化/非必要UI预加载，再对照。
